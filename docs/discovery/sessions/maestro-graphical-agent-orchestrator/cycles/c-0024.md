## An observer vetoed the thing it observes

Installing the ecosystem's one dedicated Copilot plugin **broke an unrelated live
Copilot session**: every tool call refused, `pwd` included, with
`Denied by preToolUse hook from "copilot-cmux" (hook errored)`.

Copilot treats a **non-zero exit from `preToolUse` as a denial**, and the plugin
set `exitCode = 1` on any internal error - including a payload shape it did not
recognise, which is exactly what 1.0.81-5 sends. A plugin whose entire job is
drawing status pills had become a veto over tool execution.

**Its own 68 tests passed before and after.** They only ever exercised the payload
shape it assumed. This is the **third** occurrence of the same class in this
project, after the c-0016 fuse claim and the c-0021 negative control that passed
while testing nothing - and it happened in a cycle explicitly trying to honour
that lesson, because the suite was run and trusted before installation.

Forked to `maestro-cmux/` with attribution retained, fixed to fail open, and 12
fail-open tests added across nine malformed payload shapes and every hook, with a
negative control that fails if the runner never executed. 80/80 pass.

## What the ecosystem does not have

Two delegated surveys of 190+ projects agree: **nothing enforces one worktree per
workspace**, **nothing distinguishes a deliberate stop from a crash**, and
**nothing renders a genuine parent-child agent hierarchy** - every one is a flat
board, a lane group, or a widget. The Copilot hook surface carries **no subagent
event at all**, so the ecosystem fakes trees by convention, and Maestro's
event-log join is a path none of them found.

Licensing constrains reuse: `cmux-agent-mcp` is **PolyForm Strict**, prohibiting
commercial use; `cmuxlayer` is Apache 2.0 and safe as a reference.

## Composition settled

*User: "So - Maestro becomes a form of a cmux plugin, running ontop of cmux? I'm
not opposed."* The recorded answer is narrower than the question. Maestro is
**three surfaces, and only two are host-shaped**: a Copilot CLI plugin, a
pane-hosted helper, and a **Fleet core** - enforced worktrees, durable intent,
sweep-on-launch - that is ordinary software over git, a state file, and the
process table, and needs no Host Application at all.

Maestro therefore **presents** as a plugin and is **not built** as one, which is
what keeps the route register meaningful instead of collapsing the product onto a
single host. The presentation seam is a backend interface built now rather than
retrofitted, on delegated research that retrofitting one is painful.
