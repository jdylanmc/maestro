## Questions and Answers

Three grounded questions of twelve; the group closed at 3.

**Q1 - what should a stale attention badge do?** The loop recommended expiring it
on a timer. **The answer rejected the framing of both options offered**, and was
better than either: *"copilot pauses and waits - so it should do the same. just
be present until i've addressed it, then when copilot starts churning again it
goes back to the working animation."* Attention is a **mirror of runtime state**,
not a notification with a lifetime. A 15-minute expiry would have erased a real
block: the measured maximum wait this cycle was **13432 s (3.7 hours)**.

**Q2 - does `preToolUse` stay?** The loop recommended keeping it, arguing the
veto risk was bounded because 48 payload combinations are verified
silent-and-zero. The user refused on lived evidence: *"at one point all of my
copilot sessions were busted because of this."* **The recommendation was wrong
and was withdrawn.** The c-0024 plugin that denied every tool call had **68
passing tests**; a suite cannot bound the risk of an unknown payload shape,
which is the failure mode, and citing ours as if it could was the same reasoning
error one fork later. The trade is also asymmetric: every tool call in every live
Session, against a badge clearing a few seconds sooner.

**Q3 - context usage: honest proxy, or nothing?** The loop recommended a
compaction marker and reported that no percentage exists. The user overruled: *"I
would love to see a percentage."* **The overrule was correct** - see below.

## Decisions

- **Attention is derived from the event log, never stored.** A hook fires only to
  trigger a recompute; the unmatched-`requestId` predicate in the log is the
  truth. This is the cycle's main result and it came out of the Q2 objection.
- **`preToolUse` is removed**, executing the c-0029 decision no cycle had
  performed. Deriving Attention removed the only reason to keep it.
- **`notification` and `agentStop` are registered.** Both are required because a
  Session blocked on the operator runs no tools, so no tool hook fires while the
  state that most needs reporting is true.
- **Two kill switches, not one.** Maestro honours cmux's own
  `CMUX_COPILOT_HOOKS_DISABLED=1` and adds `MAESTRO_DISABLED=1`, so this plugin
  can be silenced without disabling cmux's native Copilot integration.
- **No failed-subagent state.** `subagent.failed` is never emitted; the red
  `xmark` requirement is deleted rather than implemented.
- **Ship the context percentage, read from the runtime's own status line.** The
  synthetic estimate stays refused.

## Evidence

- **A hook-driven observer cannot report a blocked Session.** Ordering measured:
  `tool.execution_start` -> `preToolUse` -> `permission.requested`. The hook
  fires before the block exists, and nothing fires while the operator is being
  waited on. This turns #36 from an accident into a structural property.
- **`subagent.failed` does not exist.** 60 sessions: 133 `subagent.started`, 132
  `subagent.completed`, **0** failed. `subagent.completed` carries no success
  flag. c-0016 and c-0020 both recorded it from **typings** - a declaration read
  as a behaviour, the third instance of that evidence class in this session and
  the longest-lived at nine cycles.
- **The attention hooks were never registered.** `hooks.json` is generated by
  `install.sh`, so a hand-edit is discarded. Every ASK badge seen during
  development came from a hand-injected fixture.
- **Context percentage exists after all**, and the earlier unavailability claim
  came from a scan of three event types. A full scan found `tokenLimit = 936000`
  and `currentTokens = 644933` on the compaction events, and
  `cmux read-screen` returns Copilot's own status line -
  `Claude Opus 5 · Medium · 1M context (40%)` - measured at 21%, 14%, and 40%
  across three live Sessions.
- **The sidebar's animation ceiling is 1 fps** for anything hand-drawn
  (`clock.epoch` is seconds), but `ProgressView()` resolves to a native
  `AXBusyIndicator` and escapes the tick entirely. **Hover is impossible**, and
  the upstream guide says so outright.
- **Surface ownership is published, not inferred.** `CMUX_SURFACE_ID` equals the
  sidebar's `t.id`. cmux types every Copilot Session as `terminal`, so it has no
  type to expose and the title-suffix heuristic was rejected.
- A first attempt at the per-subagent attention join produced a plausible
  `129 SUBAGENT` table built entirely from guessed field names that were all
  `None`. Discarded and re-run against dumped payload shapes.

## Limitations

- **The end-to-end ASK path is unproven.** The hooks are registered but have
  never been observed firing into Maestro, because Copilot binds plugins at
  session start and every Session running during this cycle carried the old
  six-hook set. It needs a newly started Session.
- The derived-Attention design is **decided, not implemented**; the plugin still
  stores the flag.
- The per-subagent attention join is measured on completed requests only; no
  unmatched request was observed live this cycle.
- The 60-session `subagent.failed` scan reads the last 4 MB of each log, so it
  bounds the observed frequency at zero rather than proving the event can never
  be emitted.
- Context-percentage scraping is brittle by construction and was measured on one
  machine, one cmux version, one Copilot version. One of three Sessions returned
  no match because its status line was outside the viewport.
- A legacy `~/.copilot/hooks/maestro-herdr-fleet.json` from the retired herdr
  prototype still executes on every session start and tool call. Disclosed, not
  removed - outside this loop's write scope.
- Node `History` fields still exceed the schema's five-entries-plus-compaction
  bound. Fifth cycle disclosed, fifth cycle not fixed.
- **This cycle's step 14 was sequenced wrongly, and the defect is recorded
  rather than hidden.** `scripts/check-public.sh` runs at commit time and can
  *force a content change*, so it must execute **before** the exit digests are
  computed. It did not. It rejected an illustrative permission-prompt value in
  the appended evidence as employer-specific - the exact hazard that same
  paragraph documents - and redacting it changed `evidence.md` after the exit
  digest had been computed and the checkpoint rendered around it. The candidate
  had not been committed, so it had reached no consumer and was still a
  candidate rather than a published immutable artifact; it was re-rendered with
  the corrected digest `bb532cd4` and the digest-control block rewritten to
  match. Had the commit succeeded first, this would have been an immutable
  checkpoint carrying a digest that did not match disk, and the **next** cycle
  would have reported drift that never happened. The ordering fix for c-0031:
  run the public-content check as the last item before item 4.
